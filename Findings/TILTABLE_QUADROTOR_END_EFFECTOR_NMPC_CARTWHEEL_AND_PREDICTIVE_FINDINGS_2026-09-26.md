# 1. Purpose of this document

The previous end-effector NMPC update established a reusable fixed-end-effector pitch/roll benchmark and a smooth rate-coupled empirical compensation law. At that point the controller had demonstrated full 360° pitch and roll rotations about a nearly fixed end-effector point.

This document records the next phase of the project.

The main questions investigated were:

1. Can the same end-effector-centric NMPC execute a continuous **vertical cartwheel / body-Z rotation** while keeping the tool point fixed?
2. What actually happens to the four tiltable rotors as the vehicle passes through the low-thrust/singular configurations?
3. Are the difficult orientations themselves uncontrollable, or are the errors caused by **transitioning through them**?
4. Is the existing zero-thrust tilt-angle continuity rule dynamically appropriate?
5. Can future trajectory information be used to **pre-position unloaded rotors** before they become load-bearing again?
6. Does predictive pre-positioning improve the maneuver without changing the NMPC formulation?
7. What is the true 100 Hz computational cost once reference-horizon generation is included, rather than timing acados alone?
8. Is the current state sufficiently mature to freeze and move on to general 6-DoF tool trajectories?

The final conclusion is:

\[
\boxed{
\text{The cartwheel is controllable and the difficult poses are statically feasible.}
}
\]

The remaining cartwheel error is primarily associated with **load transfer and tilt-state transition of rotors that pass through near-zero thrust**.

Predictive low-thrust rotor pre-positioning reduced the important 180° and 270° transition errors while preserving the requested wrench essentially to machine precision.

The main remaining implementation limitation is computational: the current Python reference-horizon generation consumes most of the 10 ms controller budget even without predictive pre-positioning.

The cartwheel milestone is therefore considered **good enough to freeze for the current simulation/research stage** rather than continuing to optimize one benchmark.

# 4. Why the cartwheel was the next useful benchmark

Pitch and roll had already shown that the controller could:

- track large rotations,
- keep a fixed end-effector point,
- handle tilt servos through very large physical angles,
- preserve solver stability,
- exploit the omnidirectional actuation of the vehicle.

The next benchmark needed to test something qualitatively different.

The cartwheel was selected because it forces the allocator and NMPC to pass repeatedly through configurations where **one opposite rotor pair becomes nearly unloaded while the other pair temporarily carries almost the entire vehicle weight**.

This directly tests:

- load transfer between rotor pairs,
- low-thrust reference degeneracy,
- tilt-angle branch continuity,
- servo dynamics during singular/near-singular allocation,
- prediction through actuator re-engagement.

---

# 5. Cartwheel geometry

The cartwheel is not ordinary body roll.

The vehicle is initialized at:

\[
+90^\circ
\]

roll, then performs a full rotation about its **local/body/tool Z axis**.

The desired orientation is:

\[
\boxed{
q_{WE}(\gamma)
=
q_x(+90^\circ)
\otimes
q_z(\gamma)
}
\]

where:

\[
\gamma:0\rightarrow2\pi.
\]

The desired tool-frame angular velocity is:

\[
\omega_E=
\begin{bmatrix}
0\\
0\\
\dot\gamma
\end{bmatrix}
\]

and:

\[
\dot\omega_E=
\begin{bmatrix}
0\\
0\\
\ddot\gamma
\end{bmatrix}.
\]

Because the tool frame is aligned with the body frame, this is also the desired body-axis spin.

---

# 6. Why the end-effector point can remain fixed during the cartwheel

The tool offset is:

\[
r_{BE}^B=
\begin{bmatrix}
0\\
0\\
0.15
\end{bmatrix}.
\]

The cartwheel rotation is around the same body/tool Z axis.

A rotation about Z leaves the Z-axis vector invariant:

\[
R_z(\gamma)
\begin{bmatrix}
0\\
0\\
d
\end{bmatrix}
=
\begin{bmatrix}
0\\
0\\
d
\end{bmatrix}.
\]

Therefore:

\[
R_x(90^\circ)R_z(\gamma)r_{BE}
=
R_x(90^\circ)r_{BE}.
\]

The world-space body-to-tool offset is constant during the entire body-Z spin.

Also:

\[
\omega\times r_{BE}=0
\]

because both vectors lie on the same axis.

Therefore, unlike fixed-pivot pitch and roll, the CoG does **not** need to orbit around the tool.

The ideal cartwheel reference has:

- fixed end-effector position,
- fixed body origin position,
- changing orientation only.

This makes the geometry simple even though the actuator behavior is challenging.

# 8. Important cartwheel initialization decision

A normal level-hover experiment can start with:

```text
alpha = [0,0,0,0]
```

because all four rotor thrust axes initially align with body +Z, which also aligns with world up.

That is not true at +90° roll.

At +90° roll:

- body +Z is horizontal in world,
- `alpha = 0` would produce thrust horizontally,
- an all-zero tilt initialization cannot directly support gravity.

Starting the cartwheel with zero physical tilt would therefore introduce an artificial falling/servo-transient event unrelated to the benchmark.

The cartwheel runner was changed so that:

1. the trajectory is sampled at `t=0`,
2. the equivalent body reference is built,
3. the stage-0 actuator reference is generated/refined,
4. the physical external servo state is initialized from that valid stage-0 tilt reference.

This is an **experiment initialization choice**, not a bypass of the controller.

It ensures the benchmark starts at the desired +90° equilibrium instead of testing recovery from an intentionally invalid rotor geometry.

The vehicle weight is:

\[
mg
=
3.039\times9.81
=
29.81259\text{ N}.
\]

The world-frame force required for steady altitude is approximately:

\[
F^W=
\begin{bmatrix}
0\\
0\\
mg
\end{bmatrix}.
\]

For the cartwheel orientation:

\[
R_{WB}
=
R_x(90^\circ)R_z(\gamma).
\]

The same world-up force expressed in body coordinates is:

\[
F^B
=
R_{WB}^T F^W.
\]

This simplifies to:

\[
\boxed{

=

\begin{bmatrix}

\end{bmatrix}

\]

ignoring the smaller force corrections used for tracking.

This equation explains the load transfer.

The required gravity-compensation force rotates continuously in the **body XY plane** as the vehicle spins about body Z.

# 12. Why the rotor tilts sit near 86.6° / 93.4° instead of exactly 90°

The rotor angles are not chosen only to create the translational force.

The allocator must satisfy the full six-dimensional wrench:

\[
W=
\begin{bmatrix}
F_x\\
F_y\\
F_z\\
\tau_x\\
\tau_y\\
\tau_z
\end{bmatrix}.
\]

The rotor arm moments and reaction-torque contribution:

```text
KQ / KT:
0.0165 m
```

must also be balanced.

Therefore the loaded rotors typically settle slightly to either side of 90°, for example:

```text
+86.566 deg
+93.434 deg
-86.566 deg
-93.434 deg
```

rather than exactly ±90°.

This allows the allocator to produce the desired lateral body force while simultaneously cancelling unwanted body-Z force and torque components.

# 15. Observation at the low-thrust crossings

At 90°, 180°, and 270°, two rotors approach zero thrust.

When:

\[
f_i\rightarrow0,
\]

the corresponding tilt angle becomes weakly defined from the wrench perspective because:

\[
h_i=f_i\sin\alpha_i\rightarrow0
\]

and:

\[
v_i=f_i\cos\alpha_i\rightarrow0
\]

for any finite:

\[
\alpha_i.
\]

At exactly zero thrust:

\[
F_i=0
\]

regardless of the rotor angle.

This creates both a challenge and an opportunity:

- challenge: the allocator loses a meaningful instantaneous angle direction for that rotor,
- opportunity: the servo can potentially move almost freely while the rotor is unloaded, because changing its direction has very little effect on the vehicle wrench.

# 18. What the static tests prove

The static tests strongly show that:

\[
\boxed{
\text{90°, 180°, and 270° are valid controllable equilibria.}
}
\]

The drone does not lose the ability to support itself at those orientations.

Two rotors can carry the required load within the thrust limit, and the controller can maintain the full pose essentially exactly.

Therefore the 25–28 mm errors in the moving cartwheel are not explained by:

- insufficient thrust,
- a fundamentally infeasible orientation,
- an uncontrollable static wrench,
- a solver failure.

This shifted the diagnosis toward the **transition through low thrust**.

# 19. Important limitation of the static test

The static experiment should not be over-interpreted.

Each static run was initialized:

- exactly at the desired body pose,
- exactly at a valid stage-0 actuator equilibrium.

Therefore the test proves:

> a good equilibrium exists and the NMPC can maintain it.

It does **not** prove:

> the vehicle can transition into that equilibrium from an arbitrary previous tilt configuration without error.

That distinction became central to the next diagnosis.

# 20. Existing zero-thrust tilt-reference rule

The current reference generator contains the logic:

```python
if thrust_ref[rotor] <= ZERO_THRUST_EPS:
    alpha_ref[rotor] = previous_alpha[rotor]
```

where:

```text
ZERO_THRUST_EPS:
1e-8
```

The reason for this rule is valid.

When:

\[
f_i\approx0,
\]

the angle returned by:

\[
\alpha_i=\operatorname{atan2}(h_i,v_i)
\]

has no useful physical meaning and can be dominated by tiny numerical noise.

Holding the previous angle avoids:

- arbitrary branch jumps,
- `atan2(0,0)`-type behavior,
- meaningless large servo-reference changes.

This was a sensible numerical continuity rule.

---

# 21. Why the zero-thrust hold rule is dynamically suboptimal

The cartwheel exposed a weakness that was not visible in static allocation.

Consider a rotor approaching zero thrust.

The current rule effectively does:

```text
rotor loses thrust
↓
freeze previous tilt reference
↓
vehicle crosses the zero-thrust configuration
↓
rotor becomes load-bearing again
↓
only then does the reference require the new useful angle
↓
finite 48 ms servo dynamics must catch up
```

But the useful force direction reverses across the crossing.

For example, R1/R3 are required to create +Y body force on one side of the 90° crossing and -Y body force on the other side.

At exactly 90° their required thrust is nearly zero.

That low-thrust interval is the best possible time to reposition the servo.

Instead, the original continuity rule wastes that opportunity.

The result is:

- thrust begins to return,
- the rotor is still moving toward its new useful angle,
- the other pair must compensate,
- tool and attitude errors spike.

---

# 22. Key dynamic insight

The central cartwheel insight is:

\[
\boxed{
\text{When a rotor is unloaded, its tilt angle becomes a free preparation variable.}
}
\]

Instead of treating:

\[
f_i\approx0
\]

as a reason to freeze the servo reference, it can be treated as a window in which to move the rotor toward the direction it will need when thrust returns.

This led to predictive low-thrust rotor pre-positioning.

---

# 23. Predictive pre-positioning objective

The predictive method was designed to be:

- trajectory-general,
- not cartwheel-specific,
- reference-layer only,
- exact-wrench preserving where possible,
- bounded by the existing physical actuator limits,
- fallback-safe.

The algorithm is not:

```text
if cartwheel angle is near 90 deg:
    force a hard-coded rotor angle
```

Instead it uses:

\[
\boxed{
\text{future desired wrench + future actuator loading + current actuator state}
}
\]

from the existing NMPC prediction horizon.

---

# 24. Predictive horizon information

The NMPC already builds a:

```text
2.0 s
```

future reference horizon with:

```text
0.1 s
```

shooting intervals.

Therefore the reference layer already knows, at each control update:

- future body/tool references,
- future desired feedforward wrenches,
- future coarse rotor thrust references,
- future coarse rotor tilt references.

The predictive layer reuses this information.

No new motion predictor is required.

\[

\]

```text

```

are ignored.

# 26. Predictive event detection

For each rotor, the reference horizon is scanned for:

1. the beginning of a low-thrust interval,
2. a future confirmed loaded interval,
3. the future useful tilt branch at re-engagement.

If no reliable re-engagement is found inside the current prediction horizon, the baseline reference is left unchanged.

This prevents the controller from moving a rotor based on an uncertain or too-distant future demand.

---

# 27. Future angle selection

The future useful angle is not used blindly.

Because:

\[
\alpha
\]

and:

\[
\alpha\pm2\pi
\]

represent the same thrust direction but different physical servo travel, the future angle is mapped to the mechanically admissible equivalent closest to the current branch.

The existing branch-continuity concept is therefore retained.

The predictive layer changes **when** the rotor begins moving, not the basic physical interpretation of equivalent tilt branches.

---

# 28. Smooth pre-position profile

Once a future angle is identified, the unloaded rotor is smoothly moved toward it using a quintic smootherstep.

The first low-thrust node is intentionally left unchanged.

Therefore stage 0 does not receive an artificial instantaneous reference jump.

The future shooting nodes smoothly change from:

\[
\alpha_{\text{start}}
\]

toward:

\[
\alpha_{\text{future}}.
\]

Conceptually:

```text
loaded
↓
thrust falls below low-thrust threshold
↓
first low-thrust node unchanged
↓
future horizon nodes smoothly rotate servo
↓
future re-engagement angle reached
↓
rotor becomes load-bearing again
```

---

# 29. Wrench-preserving reallocation

The predictive implementation was intentionally not allowed to modify tilt angles and simply hope NMPC corrected the resulting wrench error.

Instead, every modified reference stage attempts to preserve:

\[
\boxed{
A z=W_{\text{ref}}
}
\]

exactly.

This is the key safety property of the reference heuristic.

---

# 30. One-rotor exact reallocation

If one low-thrust rotor is being pre-positioned:

- its desired preview angle is fixed,
- its small baseline thrust magnitude is retained,
- the remaining three rotors provide six free virtual components.

The remaining system is:

```text
6 wrench equations
6 free virtual components
```

and can be solved exactly when the reduced matrix is well conditioned.

---

# 31. Two-rotor exact reallocation

The cartwheel often unloads two opposite rotors simultaneously.

For two pre-positioned rotors:

- both tilt angles are prescribed,
- their two thrust magnitudes remain unknown,
- the two remaining rotors contribute four free virtual components.

Unknown count:

```text
2 fixed-angle rotor thrust magnitudes
+
4 h/v components from the other two rotors
=
6 unknowns
```

matching the six desired wrench equations.

This allows simultaneous preparation of the unloaded pair while still preserving the full body wrench.

---

# 32. Predictive safety/fallback checks

A predictive stage is rejected if any of the following occurs:

- more than the supported number of rotors require simultaneous preview,
- the reduced solve is poorly conditioned,
- the reduced solve is singular,
- a fixed/pre-positioned rotor would need more than the allowed low thrust,
- any rotor thrust exceeds the 23 N limit,
- a servo reference exceeds the NMPC angle bound,
- the reconstructed physical commands no longer reproduce the desired wrench,
- wrench residual exceeds:
  \[
  10^{-7}.
  \]

The fallback hierarchy is:

```text
try simultaneous two-rotor preview
↓ if not valid
try one rotor
↓ if not valid
use original baseline reference
```

Therefore predictive pre-positioning is an enhancement to the baseline reference generator rather than a mandatory control path.

# 40. Timing instrumentation: a major correction to the earlier interpretation

Earlier project timing conclusions were based mainly on:

```text
command.solve_time_s
```

which is acados solve time.

That is useful for evaluating the optimizer itself, but it is **not** the complete 100 Hz controller computation.

The real control-cycle budget must include:

\[
t_{\text{controller}}
=
t_{\text{reference horizon}}
+
t_{\text{parameter/warm-start work}}
+
t_{\text{acados}}
+
t_{\text{wrapper overhead}}.
\]

Instrumentation was therefore added for:

```text
reference_generation_time_ms
solve_time_ms
total_controller_time_ms
```

and the actual 10 ms deadline metric was changed to the complete:

```text
controller.solve(...)
```

wall-clock duration.

This supersedes the earlier conclusion that the current Python controller had a large real-time margin based on ~1 ms solver time alone.

# 44. Current real-time interpretation

The correct current conclusion is:

- acados itself is usually comfortably below 10 ms,
- the complete Python reference-generation/controller wrapper is not consistently below 10 ms,
- the baseline already misses the strict 100 Hz wall-clock target,
- predictive pre-positioning adds modest additional cost,
- this is currently an **implementation-performance limitation**, not evidence that the control formulation is too computationally expensive.

For simulation and continued research, this is acceptable.

For real hardware at a strict 100 Hz deadline, optimization would become necessary.

Likely future optimization directions include:

- vectorizing repeated reference calculations,
- removing repeated array allocations,
- caching constant allocation matrices and index structures,
- reducing duplicate body/tool conversions,
- avoiding repeated pseudoinverse/refinement work where possible,
- moving critical reference-generation code to compiled Python/C++,
- evaluating whether all 21 shooting-node actuator-reference refinements need to be recomputed from scratch every 10 ms.

No such optimization was required for the current milestone.

# 45. Predictive safety and reliability assessment

The current predictive method has several good properties:

## 45.1 It is not cartwheel-specific

It depends on future actuator loading and desired wrench, not on hard-coded cartwheel angles.

## 45.2 It acts only on reference generation

The validated plant dynamics and NMPC OCP remain unchanged.

## 45.3 It preserves the desired wrench

Measured maximum exact-wrench residual:

\[
1.164\times10^{-10}.
\]

## 45.4 It has physical limit checks

It rejects references violating thrust or servo-angle limits.

## 45.5 It checks numerical conditioning

Poorly conditioned reduced solves are rejected.

## 45.6 It has fallback behavior

A failed predictive modification returns to the existing baseline reference rather than forcing a bad command.

## 45.7 It produced zero full-stage fallbacks in the tested cartwheel

All:

```text
3599
```

attempted preview stages were successfully applied.

---

# 46. Why it is not yet a hardware-ready guarantee

The current simulation still has important idealizations.

The plant and NMPC share the same identified nominal model.

The cartwheel tests do not yet include:

- thrust-model mismatch,
- servo time-constant mismatch,
- external disturbances,
- aerodynamic drag uncertainty,
- motor dynamics beyond the current model,
- sensor noise,
- actuator saturation uncertainty,
- timing jitter representative of the final onboard computer,
- communication delay,
- real structural flexibility.

The predictive thresholds are also engineering heuristics selected conservatively rather than formally optimized.

Therefore the correct claim is:

> Predictive pre-positioning is numerically safe and useful in the current validated simulation architecture.

It should not yet be described as hardware-proven.

## 51.1 A 1.5 s pitch/roll rate ramp is a reasonable final cleanup

The directly tested roll result improved modestly without changing architecture.

## 51.2 The +90°-roll body-Z cartwheel is a valid end-effector benchmark

The controller can complete a full 360° rotation while keeping the tool within about 12 mm RMS.

## 51.3 Two motors can safely carry the vehicle at the cardinal cartwheel orientations

The loaded pair requires approximately:

\[
14.93\text{ N/rotor}
\]

against a:

\[
23\text{ N}
\]

limit.

## 51.4 The cartwheel is fundamentally a continuous force handover between orthogonal rotor pairs

The gravity-compensation force rotates in the body XY plane according to:

\[
F^B
=
mg[\sin\gamma,\cos\gamma,0]^T.
\]

## 51.5 The difficult regions are the pair-unloading/re-engagement transitions

The largest errors occur near:

```text
90 deg
180 deg
270 deg
```

rather than the diagonal shared-load configurations.

## 51.6 The cardinal poses themselves are not uncontrollable

Independent static 90°/180°/270° holds were essentially exact.

## 51.7 The current zero-thrust angle-hold rule is numerically sensible but dynamically incomplete

Holding previous alpha avoids meaningless branch jumps but wastes the unloaded interval.

## 51.8 Low-thrust intervals can be used to prepare the servo for future load

This is the core predictive-prepositioning insight.

## 51.9 Predictive reference generation can preserve the complete desired wrench

# 52. Superseded or deliberately rejected approaches

## 52.1 Independent pre/post fixed-point bias scheduling

From the previous phase, this was superseded because it improved translation but caused poor attitude settling due to reference anticipation.

Preferred pitch/roll bias law remains:

\[
\Delta p_E=k_b\dot\psi.
\]

## 52.2 Treating zero-thrust alpha as a meaningful instantaneous direction

At zero thrust, the angle is physically underdetermined from wrench alone.

The existing previous-angle hold rule avoids numerical noise.

## 52.3 Leaving unloaded rotors frozen until thrust returns

This is now understood as dynamically suboptimal for trajectories like the cartwheel.

## 52.4 Hard-coded cartwheel-angle servo switching

This was deliberately avoided.

Predictive behavior is based on future load/wrench information, not hard-coded 90°/180°/270° cases.

## 52.5 Further tuning of predictive thresholds

Not pursued because the current benchmark is already sufficient to validate the concept and project effort is better spent on more general trajectories.

The following should remain explicit in future reports:

1. **Static pose tests start at equilibrium.**  
   They prove feasibility, not recovery from arbitrary actuator states.

2. **Predictive thresholds are heuristic.**  
   They have not been globally optimized.

3. **The predictive result is mixed.**  
   180° and 270° improve strongly; 90° does not.

4. **Overall tool RMS does not improve.**  
   Predictive:
   `12.047 mm`; baseline:
   `11.988 mm`.

5. **Worst-case error does improve.**  
   Predictive tool max:
   `26.229 mm`; baseline:
   `28.465 mm`.

6. **Current complete Python controller is not strictly 100 Hz real-time-safe.**

7. **The simulation remains nominal/matched.**

8. **No real-hardware validation has been performed.**

9. **The cartwheel empirical results should not be generalized to arbitrary mass, inertia, servo, tool-offset, or propulsion configurations without re-testing.**

# 54. Recommended next technical milestone

The fixed-point maneuver sequence has now covered:

```text
large-angle pitch
↓
large-angle roll
↓
continuous body-Z cartwheel
↓
low-thrust pair handover
↓
predictive unloaded-rotor preparation
```

The next useful question is no longer:

> Can we optimize one particular rotation a little more?

It is:

\[
\boxed{
\text{Can the same end-effector NMPC track a general simultaneous 6-DoF tool trajectory?}

- X/Y/Z translation,
- simultaneous roll/pitch/yaw orientation change,
- nonzero tool velocity,

\[
\boxed{

rather than a maneuver-specific special case.
